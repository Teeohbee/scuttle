Every watch ends with something on screen. Don't skip a "run it" checkpoint - this is a game about feel, and you can't proofread feel.

Powder Monkeys is a game for up to six people about keeping a ship fighting. One deck, one enemy that never stops firing, and more jobs than there are hands: someone has to fetch powder, someone has to ram the gun, and while they do it the hold is on fire and the ship is taking water. Nobody holds it together alone - that's the whole design.

By the end you will have built all of it from an empty folder: the hull, the crew and their controllers, the stations, the three hazards, the enemy, and the interface that lets a player read the situation at a glance. Eleven watches, each ending with something you can run. Every script is given complete - nothing later depends on a file this guide hasn't shown you.

WATCH 0

A new project, set up before you build anything

  1. Project Manager → New/Create Project. Name it Powder Monkeys, pick an empty folder, and set the renderer to Compatibility - this is 2D pixel art with no need for the Forward+ renderer.
  2. Open the project. In Project → Project Settings → Display → Window, set Viewport Width 640, Viewport Height 360, and Window Width/Height Override 1280 × 720. Under Stretch set Mode viewport, Aspect keep_width, Scale Mode integer - exact ×6 on a 4K TV, ×2 on a Steam Deck.
  3. In Rendering → Textures → Canvas Textures, set Default Texture Filter to Nearest.
  4. Download the Monochrome Pirates and Monochrome RPG asset packs from kenney.nl (both free, CC0) and unzip their dot-matrix/ folders into your project under assets/kenney_monochrome-pirates/ and assets/kenney_monochrome-rpg/. Each contributes one sheet, tilemap.png, 16×16 tiles, 1px separation, 17 columns wide.
How scenes actually get made, once, so the rest of this guide can say it tersely

Creating a scene's first (root) node: Scene dock → Scene → New Scene (or the empty Scene dock shows big buttons - 2D Scene, 3D Scene, User Interface, Other Node - click Other Node to search for any type by name, e.g. CharacterBody2D). Adding a child to an existing node: select the parent in the Scene dock, click the + icon in its toolbar (or Ctrl+A), search the type, click Create. Renaming: double-click the node's name in the Scene dock, or select it and press F2. Saving: Ctrl+S the first time prompts for a path - type the full res://... path this guide gives you. Attaching a script: select the node, click the scroll-with-a-plus icon in the Scene dock toolbar. Wiring a node reference in the Inspector: whenever a script declares a typed node export such as @export var hull: TileMapLayer, the Inspector shows a drag target for it - drag the target node from the Scene dock straight onto that field; you never type a path by hand.

Register all three as autoloads: Project → Project Settings → Autoload, browse to each script, leave the node name as its filename's PascalCase (GameState, PlayerRegistry, Fx), click Add. Each is now reachable from anywhere by that name.

Why lose() checks a flag but win() doesn't

The sandbox in Watch 10 exists so you can stand in a burning ship and study how the fire spreads without the run ending under you. Putting that switch inside GameState.lose() means it's honoured by every hazard automatically - no hazard script ever has to know the sandbox exists. Winning stays possible in the sandbox, because sinking the enemy is a thing you're often deliberately practising.

Why an autoload, not a regular node

An autoload is a script Godot instantiates once, before any scene loads, and keeps alive for the whole run regardless of which scene is open. It's Godot's global singleton. Anything that must survive a scene change - whose player is which, whether the battle is won - belongs here, not on a node a scene change frees.

Run it

You have registered three autoloads and written no scenes, so Godot has nothing to run. Will the Output panel simply be empty, or will those three scripts have run anyway?

What should happen

They run anyway - that is what makes them autoloads, and it is why the rest of the guide can call GameState from anywhere without wiring it. So the panel should be clean but not idle: no "node not found", no null instance. An error here means a path in the Autoload list is wrong, and everything you build on top of it will fail too.

WATCH 1

The hull: paint it, don't compute it

Build the ship as data painted in the editor: Godot's TileMapLayer and its built-in physics turn "which pixels are walkable" into something you paint once per tile, rather than something you write out by hand.

Build the TileSet

  1. New scene, root Node2D, rename Deck, save as res://src/ship/deck.tscn.
  2. Add a child: select Deck, Ctrl+A, search TileMapLayer, create it, rename to Hull.
  3. In the Inspector, next to Tile Set, click <empty> → New TileSet. Click the new resource to open the TileSet editor at the bottom of the screen.
  4. In the Setup tab, drag in assets/kenney_monochrome-pirates/dot-matrix/tilemap.png as an Atlas source (16×16 tile size, Separation 1, 1); repeat for the RPG pack's sheet as a second source.
  5. Add a Physics Layer (Inspector → "Physics Layers" array → Add Element). In the TileSet editor's Select tool, click each wall/rail tile and, in its per-tile panel's Physics tab, draw a polygon over just the tile's solid band.
  6. Add a Custom Data Layer: with the TileSet resource selected, Inspector → Custom Data Layers → Add Element. Set its Name to room and its Type to String. This is how a tile says which room it belongs to, so fire and leak messages can name a place and fire can tell a room from the open corridor.
  7. Now make eight alternative tiles of your floor tile, one per room - read the trap below first, because this is the step the whole hazard system rests on.

Known trap - custom data belongs to the tile, not to the cell you paint

The natural reading of "tag each room's floor with its name" is that you paint a cell and then type a room name onto that cell. There is no such feature, and looking for it is a long, demoralising hunt through the TileMap panel.

Custom data is a property of a tile in the TileSet. Every cell painted with that tile returns the same room string, because they are all the same tile. One floor tile can therefore only ever mean one room.

The fix is alternative tiles: same texture region, separate TileData, so each can carry its own custom data. In the TileSet editor's Select mode, click your floor tile; the panel to the right of the atlas shows that tile's alternatives with a + to add one. Add eight, and give each one a room value from the table below. Leave the base floor tile's room empty - that's the one you paint the corridor and the doorways with.

When you paint, all eight alternatives appear in the tile palette beside the base tile. Picking the right one per room is the tagging step.

Why paint collision instead of writing it

Painting a physics polygon onto each tile in the TileSet editor is "which pixels are floor," entered once, in the place built to hold it - every room you paint with that tile inherits its collision automatically, and no script anywhere needs to describe the hull's shape a second time.

Quickest way to check you got it right, before you write a line of hazard code: select Hull, and in the TileMap panel hover a cell - the tile's custom data shows in the Inspector when you select its tile in the TileSet editor. Or just wait for the Watch 10 layout check, which walks every station and fails loudly if one is standing somewhere that isn't a tagged floor tile.

Tune this - corridor squeeze

A mast's collider should be one tile wide in a 3-row corridor, leaving a clear lane on either side. Widen it and a crew member bounces off it instead of squeezing past. Walk a test character past every mast, both directions, before moving on.

Add a camera

  1. Add a Camera2D child of Deck, and name it Camera2D. Set its Position to the hull's centre: for the 32 × 13-tile hull at 16px tiles, that is exactly (256, 104).

WATCH 2

Get one pirate walking before you get six

Multiplayer input and a join lobby are real complexity worth deferring. Get a single CharacterBody2D walking on plain WASD first - that proves the collision from Watch 1 actually works, and it's much smaller to debug alone.

  1. New scene, root CharacterBody2D, rename Crew, save as res://src/crew/crew.tscn.
  2. Add a child Sprite2D - set its Texture to the pirates sheet, enable Region in the Inspector's Texture Region section, and set the region rect to one 16×16 cell.
  3. Add a child CollisionShape2D. In the Inspector, new CircleShape2D, radius 6.
  4. Select the Crew root node. In the Inspector under CharacterBody2D → Motion Mode, change the value from Grounded to Floating. The default Grounded mode assumes gravity and produces wrong diagonal-wall behaviour in a top-down game - Floating is required for any 2D top-down movement.
  5. Attach a script to the Crew root.
# src/crew/crew.gd
extends CharacterBody2D

const SPEED := 90.0

func _physics_process(_delta: float) -> void:
	var move := Vector2.ZERO
	move.x = int(Input.is_key_pressed(KEY_D)) - int(Input.is_key_pressed(KEY_A))
	move.y = int(Input.is_key_pressed(KEY_S)) - int(Input.is_key_pressed(KEY_W))
	velocity = move.normalized() * SPEED
	move_and_slide()

Drag crew.tscn into deck.tscn as a child of Deck, positioned somewhere on the painted corridor. This one is temporary - Watch 3 spawns the real crew at runtime, and you'll delete this instance there.

Why move_and_slide() instead of writing your own collision

CharacterBody2D is Godot's kinematic body: set velocity, call move_and_slide() once a physics frame, and it resolves collision against whatever physics bodies are nearby - including the polygons painted in Watch 1 - sliding along a wall instead of stopping dead.

Run it

Press F5 and walk the pirate about with WASD.

You painted collision onto tiles rather than writing it out. So what happens when you take a mast at an angle - a dead stop, or a slide past it? Decide, then look.

What should happen

It stops or slides, never passes through, and it slides past a mast taken at an angle. Walking straight through means the physics layer never got painted onto that tile - the collision belongs to the tile in the TileSet, not to the cell you painted with it.

WATCH 3

The whole crew, and the join screen

Now widen from one keyboard-controlled body to up to six, each on its own device, with a lobby to claim a slot before the battle starts. This watch also nails down exactly which key or button is "interact" and "join" - the rest of the game depends on both.

One device id per player

Everything downstream - crew members, stations, the join screen - identifies a player by a single integer, their device id. Gamepads bring their own: Godot numbers them 0, 1, 2 as they connect. The keyboard is the awkward one. Two people are going to share it, one on WASD and one on the arrows, and Godot reports every key from a single anonymous keyboard - there is no per-key device index the way there is for gamepads. So invent two: -1 for the WASD half and -2 for the arrows half. They are negative precisely so they can never collide with a real gamepad.

That gives one rule the rest of the build can lean on: a device id names a player, and a player has exactly one device id. Two crew on one keyboard stop being a special case anywhere except the twelve minutes you are about to spend in the Input Map.

Author the actions

Open Project → Project Settings → Input Map and add these eighteen actions. The two keyboard schemes are written out in full, because they are genuinely different bindings. The six *_pad actions are a template - bind them against any one controller and the registry will clone them per device at runtime.

ActionWASD (_wasd)Arrows (_arrows)Gamepad (_pad)
move_left_*A←Left Stick Left
move_right_*D→Left Stick Right
move_up_*W↑Left Stick Up
move_down_*S↓Left Stick Down
interact_*EShiftX (button 2)

Set the deadzone on the four move_*_pad actions to 0.25. The default of 0.5 is tuned for menu navigation and makes a crew member feel like they are wading before they have even reached the water.

Why named actions and not raw key reads

You could skip all of this and poll Input.is_key_pressed(KEY_E) directly. It is fewer clicks today and it costs you three things. Rebinding a key becomes a code change rather than an editor change. Stick deadzones and diagonal normalisation become yours to get right instead of the engine's. And, worst, you have to hand-roll "just pressed" - which means storing last frame's state and diffing it, which means getting the frame timing right, which is a bug you do not want to own in a game where every interaction in every later watch runs through a single button.

Input.is_action_just_pressed() already solves that last one properly: it records the frame of a press against both the render clock and the physics clock, and answers against whichever one you are calling from. It is a pure query, so a station and a crew member's own pickup handler can both ask about the same press, in any order, and both get the truth.

The player registry

One autoload owns two jobs: mapping a device id onto its set of actions, and keeping the roster of who has joined. Create res://src/core/player_registry.gd and register it as an autoload named PlayerRegistry. 

# src/core/player_registry.gd
extends Node

const KEYBOARD_WASD := -1
const KEYBOARD_ARROWS := -2

const MAX_PLAYERS := 6
const ACCENT_COLORS: Array[Color] = [
	Color("e05252"), Color("4f8fe0"), Color("4fbf6b"),
	Color("e0c24f"), Color("b06fe0"), Color("e08a3d"),
]

# The two hand-authored keyboard halves. Everything else is a gamepad and gets
# its suffix generated from its device number.
const SCHEME_SUFFIX := {
	KEYBOARD_WASD: "wasd",
	KEYBOARD_ARROWS: "arrows",
}
const PAD_ACTIONS := [
	"move_left", "move_right", "move_up", "move_down", "interact", "join",
]

var _players: Dictionary = {}  # device_id -> { device_id, number, color }

func _ready() -> void:
	for device_id in Input.get_connected_joypads():
		_bind_pad(device_id)
	Input.joy_connection_changed.connect(_on_joy_connection_changed)

func _on_joy_connection_changed(device_id: int, connected: bool) -> void:
	if connected:
		_bind_pad(device_id)

# Clone the six *_pad template actions into a per-device set - interact_pad0,
# interact_pad1, ... - with every event retargeted at that one controller.
# One set authored in the editor becomes one set per pad, and Input does the
# rest.
func _bind_pad(device_id: int) -> void:
	for action in PAD_ACTIONS:
		var template := "%s_pad" % action
		var per_device := "%s_pad%d" % [action, device_id]
		if InputMap.has_action(per_device):
			continue
		InputMap.add_action(per_device, InputMap.action_get_deadzone(template))
		for event in InputMap.action_get_events(template):
			var copy: InputEvent = event.duplicate()
			copy.device = device_id
			InputMap.action_add_event(per_device, copy)

func suffix(device_id: int) -> String:
	return SCHEME_SUFFIX.get(device_id, "pad%d" % device_id)

func has_device(device_id: int) -> bool:
	return InputMap.has_action("interact_%s" % suffix(device_id))

func connected_devices() -> Array:
	var out: Array = [KEYBOARD_WASD, KEYBOARD_ARROWS]
	out.append_array(Input.get_connected_joypads())
	return out

func move_vector(device_id: int) -> Vector2:
	if not has_device(device_id):
		return Vector2.ZERO
	var s := suffix(device_id)
	return Input.get_vector(
		"move_left_%s" % s, "move_right_%s" % s,
		"move_up_%s" % s, "move_down_%s" % s,
	)

func is_interact_pressed(device_id: int) -> bool:
	return has_device(device_id) and Input.is_action_pressed("interact_%s" % suffix(device_id))

func is_interact_just_pressed(device_id: int) -> bool:
	return has_device(device_id) and Input.is_action_just_pressed("interact_%s" % suffix(device_id))

func is_join_just_pressed(device_id: int) -> bool:
	return has_device(device_id) and Input.is_action_just_pressed("join_%s" % suffix(device_id))

func is_joined(device_id: int) -> bool:
	return _players.has(device_id)

func join(device_id: int) -> Dictionary:
	if _players.has(device_id):
		return _players[device_id]
	if _players.size() >= MAX_PLAYERS:
		return {}
	var number := _lowest_free_number()
	var player := { "device_id": device_id, "number": number, "color": ACCENT_COLORS[number - 1] }
	_players[device_id] = player
	return player

func players() -> Array:
	var out := _players.values()
	out.sort_custom(func(a, b): return a.number < b.number)
	return out

# Used only by the sandbox (Watch 10): board everyone who has a device plugged
# in, without anyone having to visit the join screen.
func join_all_connected() -> Array:
	for device_id in connected_devices():
		join(device_id)
	return players()

func reset() -> void:
	_players.clear()

func _lowest_free_number() -> int:
	var taken := {}
	for p in _players.values():
		taken[p.number] = true
	for n in range(1, MAX_PLAYERS + 1):
		if not taken.has(n):
			return n
	return -1
Why _bind_pad() generates actions instead of you authoring them

A gamepad event in the Input Map carries a device index, so the fully manual version of this works: author interact_pad0 through interact_pad5 by hand, six actions each, thirty-six rows in the editor. It is the standard approach and it is miserable to maintain - change the interact button and you are editing it six times, and the sixth is the one you will miss.

InputMap is writable at runtime, so bind the button once and let fifteen lines do the copying. event.duplicate() gives you a fresh event, setting .device pins it to one controller, and action_get_deadzone() carries your 0.25 across so the generated actions feel like the one you tuned.

Known trap - bind on connect, not just at startup

The obvious version of _ready() loops over Input.get_connected_joypads() and stops there. It works perfectly, right up until someone plugs a controller in after the game has launched - which, for a six-player party game, is most of them.

The failure is quiet and it points at the wrong thing. connected_devices() asks the hardware, so the new pad shows up in the list immediately and the join screen happily offers it a slot. But no join_pad3 action was ever generated, so has_device() is false and every press is dropped. The player sees a lobby that lists their controller and ignores it, and concludes their controller is broken.

Hence Input.joy_connection_changed. It fires on every plug and unplug; _bind_pad() is idempotent, so reconnecting the same pad is harmless.

Rewrite crew.gd to read a device

# src/crew/crew.gd
extends CharacterBody2D

const SPEED := 90.0

@export var device_id: int = PlayerRegistry.KEYBOARD_WASD
@export var accent: Color = Color.WHITE

@onready var _sprite: Sprite2D = $Sprite2D

func _ready() -> void:
	add_to_group("crew")
	_sprite.modulate = accent

func _physics_process(_delta: float) -> void:
	velocity = PlayerRegistry.move_vector(device_id) * SPEED
	move_and_slide()

No normalising, no deadzone, no clamp. Input.get_vector() applies the action's deadzone and caps the result at length 1, so a diagonal on the keyboard is not faster than a straight line and a half-tilted stick still walks at half speed.

Why the colour matters more than it looks

Six identical white pirates in a corridor is unplayable - not "a bit plain", genuinely unplayable, because you cannot find yourself. modulate tints the whole sprite, so one monochrome Kenney frame becomes six readable characters for free. The colours come straight from ACCENT_COLORS, assigned at join time, so a player's slot number and their colour never disagree.

Everything that reads input in this build does it from _physics_process, next to the movement it affects. That is a consistency choice rather than a correctness one - Input answers correctly from either clock - but it keeps every gameplay script on one timeline. Purely visual things like shake_camera.gd and hud.gd stay in _process, where they belong.

The join screen

  1. New scene, root Control (Layout → Full Rect), rename JoinScreen, save as res://src/ui/join_screen.tscn.
  2. Add a Label for the title, and an HBoxContainer named Slots holding six PanelContainer children, each with a Label for "P1"-"P6" and a second Label named Status for "press to join" / "joined".
  3. Attach this script to JoinScreen:
# src/ui/join_screen.gd
extends Control

func _ready() -> void:
	# Paint the slots once up front, or every slot sits blank until the first
	# person joins and the player before them wonders if the game is broken.
	_refresh()

func _physics_process(_delta: float) -> void:
	for device_id in PlayerRegistry.connected_devices():
		if PlayerRegistry.is_join_just_pressed(device_id) and not PlayerRegistry.is_joined(device_id):
			PlayerRegistry.join(device_id)
			_refresh()
	if PlayerRegistry.players().size() >= 2:
		for player in PlayerRegistry.players():
			if PlayerRegistry.is_interact_just_pressed(player.device_id):
				get_tree().change_scene_to_file("res://src/ship/deck.tscn")
				return

func _refresh() -> void:
	var joined_numbers := {}
	for p in PlayerRegistry.players():
		joined_numbers[p.number] = true
	for i in range(6):
		var slot := $Slots.get_child(i)
		slot.get_node("Status").text = "JOINED" if joined_numbers.has(i + 1) else "PRESS TO JOIN"

Why set_kind() and not just kind = ...

A full bucket becomes an empty one the instant it douses a fire, and an empty one becomes full again at the water butt. If the icon doesn't change with it, a player sprinting back to a fire with an empty bucket has no way to know - the single most confusing bug you can ship in a game about fetching things. Routing every change through one setter is what makes that impossible to forget.

	# the group happens to hand back. See the trap below.

			continue

		return

		held_item.drop(get_parent(), global_position)
		held_item = null
		return
	var nearest := _nearest_loose_item()
	if nearest:
		nearest.pick_up(hold_point)
		held_item = nearest

func _nearest_loose_item() -> Carryable:
	var best: Carryable = null
	var best_dist := PICKUP_RANGE
	for item in get_tree().get_nodes_in_group("carryables"):
		if item.held:
			continue
		var d := global_position.distance_to(item.global_position)
		if d <= best_dist:
			best = item
			best_dist = d
	return best

Claim, then act - two separate steps

_handle_interact() asks every member of the "stations" group - built in Watch 5 - whether it wants this press before generic pickup/drop touches the button at all. The station that wins both gets to act (perform_interact) and stops Crew from also treating the same press as a pickup. A predicate that only vetoes without a matching action would leave every station "interested" but nothing ever actually loading a cannon or dousing a fire - claiming and performing are two different jobs, and both matter.

Note that the loop finds the highest-priority claimer rather than stopping at the first. That matters more than it looks - see below.

The "stations" group is empty until Watch 5 - the loop simply iterates zero items and falls straight through to _pick_up_or_drop(). This is intentional: the code is already in its final shape; the group just isn't populated yet.

Known trap - "first one that says yes" is not a rule, it's a coin toss

The obvious loop stops at the first claimer and calls it done. get_nodes_in_group() returns nodes in whatever order the tree happens to hold them, so "first" is not a decision you made - it's scene-dock ordering leaking into your rules.

It bites the moment two things legitimately want the same press. A fire can break out on any floor cell, including the cell a station is standing on. Then a crew member holding a full bucket, stood in the flames at the water butt, presses interact - and the water butt claims it first, because it sorts earlier. The fire cannot be put out at all. It is roughly a one-in-twenty outbreak, it looks like the bucket is broken, and it will not reproduce when you go looking for it.

Hence interact_priority: gather every claim, then act on the strongest. An emergency outranks a chore, and the outcome no longer depends on the order nodes were added to the scene.

extends Station

signal fired(damage: float)

const RUN_OUT_HOLD_TIME := 0.8
const COOLDOWN_TIME := 1.5
const DAMAGE := 8.0

const PHASE_COLORS := {
	Phase.EMPTY:    Color(0.35, 0.35, 0.35),   # grey  - needs powder
	Phase.POWDERED: Color(0.85, 0.55, 0.15),   # amber - needs shot
	Phase.LOADED:   Color(0.90, 0.85, 0.20),   # yellow- needs ramming
	Phase.RUN_OUT:  Color(0.30, 0.85, 0.35),   # green - ready to fire
	Phase.COOLDOWN: Color(0.60, 0.20, 0.20),   # red   - too hot
}

var phase: Phase = Phase.EMPTY
var _run_out_elapsed := 0.0
var _cooldown_elapsed := 0.0

@onready var _light: ColorRect = $PhaseLight

func _ready() -> void:
	add_to_group("cannons")
	_set_phase(Phase.EMPTY)

# with the state machine.
func _set_phase(next: Phase) -> void:
	phase = next
	_light.color = PHASE_COLORS[phase]

func _physics_process(delta: float) -> void:
	match phase:
		Phase.LOADED:
			_tick_run_out(delta)
		Phase.COOLDOWN:
			_cooldown_elapsed += delta
			if _cooldown_elapsed >= COOLDOWN_TIME:
				_cooldown_elapsed = 0.0
				_set_phase(Phase.EMPTY)

# Bare hands only - you cannot ram a gun holding a barrel of powder.
func _tick_run_out(delta: float) -> void:
	var holding_bare_hands := false
	for crew in get_tree().get_nodes_in_group("crew"):
		if crew_is_near(crew) and crew.held_item == null \
				and PlayerRegistry.is_interact_pressed(crew.device_id):
			holding_bare_hands = true
			break
	if holding_bare_hands:
		_run_out_elapsed += delta
		if _run_out_elapsed >= RUN_OUT_HOLD_TIME:
			_run_out_elapsed = 0.0
			_set_phase(Phase.RUN_OUT)
	else:
		_run_out_elapsed = 0.0

func claims_interact(crew) -> bool:
	if not crew_is_near(crew):
		return false
	match phase:
		Phase.EMPTY:
			return crew.held_item != null and crew.held_item.kind == Carryable.Kind.POWDER
		Phase.POWDERED:
			return crew.held_item != null and crew.held_item.kind == Carryable.Kind.SHOT
		Phase.RUN_OUT:
			return true
		_:
			return false

func perform_interact(crew) -> void:
	match phase:
		Phase.EMPTY:
			crew.held_item.queue_free()
			crew.held_item = null
			_set_phase(Phase.POWDERED)
		Phase.POWDERED:
			crew.held_item.queue_free()
			crew.held_item = null
			_set_phase(Phase.LOADED)
		Phase.RUN_OUT:
			_set_phase(Phase.COOLDOWN)
			fired.emit(DAMAGE)

class_name FireHazard
extends Node2D

signal outbreak(cell: Vector2i)

const SPREAD_INTERVAL := 3.0
const DOUSE_REACH := 20.0
const MAGAZINE_ROOM := "magazine"

@export var hull: TileMapLayer

var _burning: Dictionary = {}    # Vector2i -> ColorRect (the burning cell's visual)
var _elapsed := 0.0
var _reported_magazine := false

# Beats any ordinary station competing for the same press.
var interact_priority: int = 10

func _ready() -> void:
	add_to_group("stations")

func _process(delta: float) -> void:
	_elapsed += delta
	if _elapsed < SPREAD_INTERVAL:
		return
	_elapsed = 0.0
	_spread()

func ignite_random() -> void:
	var candidates := _ignitable_cells()
	if candidates.is_empty():
		return
	_ignite(candidates[randi() % candidates.size()])

func claims_interact(crew) -> bool:
	if crew.held_item == null or crew.held_item.kind != Carryable.Kind.BUCKET_WATER:
		return false
	return _nearest_burning(crew.global_position) != Vector2i.MIN

func perform_interact(crew) -> void:
	var cell := _nearest_burning(crew.global_position)
	if cell == Vector2i.MIN:
		return
	_extinguish(cell)
	crew.held_item.set_kind(Carryable.Kind.BUCKET_EMPTY)

# The room name painted on a cell in Watch 1, or "" for walls, the corridor,
# and anywhere off the ship. This one function is the whole definition of
# "somewhere a fire can be".
func _room_of(cell: Vector2i) -> String:
	var data := hull.get_cell_tile_data(cell)
	if data == null:
		return ""
	var room: String = data.get_custom_data("room")
	return room

func _world_of(cell: Vector2i) -> Vector2:
	return hull.to_global(hull.map_to_local(cell))

func _ignite(cell: Vector2i) -> void:
	if _burning.has(cell):
		return
	var visual := ColorRect.new()
	visual.size = Vector2(16, 16)
	visual.color = Color(0.85, 0.25, 0.1)
	add_child(visual)
	visual.global_position = _world_of(cell) - Vector2(8, 8)
	_burning[cell] = visual
	outbreak.emit(cell)

	if _room_of(cell) == MAGAZINE_ROOM and not _reported_magazine:
		_reported_magazine = true
		GameState.lose("The magazine caught fire.")

func _extinguish(cell: Vector2i) -> void:
	if not _burning.has(cell):
		return
	_burning[cell].queue_free()
	_burning.erase(cell)

func _spread() -> void:
	var frontier: Array = _burning.keys()
	for cell in frontier:
		var room := _room_of(cell)
		for offset in [Vector2i(1, 0), Vector2i(-1, 0), Vector2i(0, 1), Vector2i(0, -1)]:
			var neighbor: Vector2i = cell + offset
			if _burning.has(neighbor):
				continue
			# Same room only. A fire never crosses a wall, never runs down the
			# corridor, and never reaches the open sea - and it can never grow
			# past the 18 cells of the room it started in.
			if _room_of(neighbor) != room:
				continue
			_ignite(neighbor)

func _ignitable_cells() -> Array[Vector2i]:
	var cells: Array[Vector2i] = []
	for cell in hull.get_used_cells():
		if _room_of(cell) != "":
			cells.append(cell)
	return cells

func _nearest_burning(from: Vector2) -> Vector2i:
	var best := Vector2i.MIN
	var best_dist := DOUSE_REACH
	for cell in _burning.keys():
		var d := from.distance_to(_world_of(cell))
		if d <= best_dist:
			best = cell
			best_dist = d
	return best

One rule, two jobs

It is tempting to filter by room only when starting a fire and let spreading use the cheaper "is there a tile here" test. That's the bug: wall tiles and corridor tiles are painted tiles, so they pass it. The fire creeps into the timbers and down the corridor, which looks like a physics glitch and is really a mismatched pair of definitions. _room_of() is used by both, so they cannot drift.

Containment is also what makes fire fair. Unbounded four-way spread doubles every tick and eats the ship faster than six people can carry buckets; bounded to one 6×3 room, the worst case is 18 cells and a crew that commits to it will always win. The corridor stays the safe artery, which is what makes it worth running down.

signal sprung(at: Vector2)

const LEAK_RATE := 3.0     # % per second, per open leak
const PUMP_RATE := 8.0     # % per second, while the pump is manned
const WADE_THRESHOLD := 50.0
const PLUG_RANGE := 12.0

@export var hull: TileMapLayer
@export var pump: Pump

var water_level: float = 0.0
var _leaks: Dictionary = {}      # int id -> { at: Vector2, visual: ColorRect }
var _next_id := 0
var _reported_flooded := false
var interact_priority: int = 10

func _ready() -> void:
	add_to_group("stations")
	add_to_group("leak_hazard")

func _process(delta: float) -> void:
	water_level += _leaks.size() * LEAK_RATE * delta
	if pump.manned:
		water_level -= PUMP_RATE * delta
	water_level = clamp(water_level, 0.0, 100.0)

	if water_level >= 100.0 and not _reported_flooded:
		_reported_flooded = true
		GameState.lose("The ship flooded.")

func crew_slowed() -> bool:
	return water_level > WADE_THRESHOLD

func spring_random() -> void:
	# Rooms only - the same rule fire uses. A leak inside a wall is unpluggable,
	# and one in the corridor turns the ship's only artery into a hazard.
	var cells := _room_cells()
	if cells.is_empty():
		return
	var cell: Vector2i = cells[randi() % cells.size()]
	var at: Vector2 = hull.to_global(hull.map_to_local(cell))

	var visual := ColorRect.new()
	visual.size = Vector2(10, 10)
	visual.color = Color(0.3, 0.5, 0.85)
	add_child(visual)
	visual.global_position = at - Vector2(5, 5)

	var id := _next_id
	_next_id += 1
	_leaks[id] = { "at": at, "visual": visual }
	sprung.emit(at)

func claims_interact(crew) -> bool:
	if crew.held_item == null or crew.held_item.kind != Carryable.Kind.PLANK:
		return false
	return _nearest_leak(crew.global_position) != -1

func perform_interact(crew) -> void:
	var id := _nearest_leak(crew.global_position)
	if id == -1:
		return
	_leaks[id].visual.queue_free()
	_leaks.erase(id)
	crew.held_item.queue_free()
	crew.held_item = null

func _nearest_leak(from: Vector2) -> int:
	var best_id := -1
	var best_dist := PLUG_RANGE
	for id in _leaks:
		var d: float = from.distance_to(_leaks[id].at)
		if d <= best_dist:
			best_id = id
			best_dist = d
	return best_id

func _room_cells() -> Array[Vector2i]:
	var cells: Array[Vector2i] = []
	for cell in hull.get_used_cells():
		var data := hull.get_cell_tile_data(cell)
		if data == null:
			continue
		var room: String = data.get_custom_data("room")
		if room != "":
			cells.append(cell)
	return cells

# src/ship/shake_camera.gd
extends Camera2D

const DECAY_PER_SECOND := 6.0
var _strength := 0.0

func _ready() -> void:
	add_to_group("shake_camera")

func shake(strength: float) -> void:
	_strength = max(_strength, strength)

func _process(delta: float) -> void:
	if _strength <= 0.0:
		offset = Vector2.ZERO
		return

A layout sanity check

Write a @tool script that walks every station's position and asserts it sits on a floor cell at edit time - failing loudly in the editor rather than silently at play-test. Save as res://tests/test_layout.gd: 

# tests/test_layout.gd
@tool
extends Node2D

@export var hull: TileMapLayer
@export var run_check: bool = false:
	set(v):
		if v and is_inside_tree():
			_check()
		run_check = false

func _check() -> void:
	if not hull:
		push_error("test_layout: hull not set")
		return
	var misplaced := []
	for station in get_tree().get_nodes_in_group("stations"):
		# Fire, Leak and Breach share this group but aren't Stations and have no
		# meaningful position - checking them would report false failures forever.
		if not (station is Station):
			continue
		var cell: Vector2i = hull.local_to_map(hull.to_local(station.global_position))
		if hull.get_cell_tile_data(cell) == null:
			misplaced.append(station.name)
	if misplaced.is_empty():
		push_warning("Layout OK - all stations on floor tiles.")
	else:
		push_error("Layout FAIL - stations off floor: %s" % str(misplaced))

Add this node to deck.tscn as a child of Deck, name it LayoutCheck, drag Hull into its Hull field, then flip the Run Check toggle in the Inspector any time you move a station - the result prints to the Output panel without pressing F5.

What @tool buys you

A script with @tool at the top runs inside the editor, not just at play time - you can print warnings straight into the editor while still painting the hull, rather than only finding out something's wrong the next time you press F5.

The finished crew.gd, assembled

crew.gd grew across four watches too - bare movement (2), reading a device and wearing a colour (3), carrying things (4), and wading through floodwater (6). Here it is whole: 

# src/crew/crew.gd
extends CharacterBody2D

const SPEED := 90.0
const PICKUP_RANGE := 14.0
const WADE_SPEED_FACTOR := 0.55

@export var device_id: int = PlayerRegistry.KEYBOARD_WASD
@export var accent: Color = Color.WHITE

var held_item: Carryable = null

@onready var _sprite: Sprite2D = $Sprite2D
@onready var hold_point: Node2D = $HoldPoint

func _ready() -> void:
	add_to_group("crew")
	_sprite.modulate = accent

func _physics_process(_delta: float) -> void:
	var move := PlayerRegistry.move_vector(device_id)

	var speed := SPEED
	var leak = get_tree().get_first_node_in_group("leak_hazard")
	if leak and leak.crew_slowed():
		speed *= WADE_SPEED_FACTOR

	velocity = move * speed
	move_and_slide()

	_handle_interact()

func _handle_interact() -> void:
	if not PlayerRegistry.is_interact_just_pressed(device_id):
		return
	# Ask everything, then act on the strongest claim - not on the first one
	# the group happens to hand back. See the trap below.
	var winner: Node = null
	var best := -1
	for station in get_tree().get_nodes_in_group("stations"):
		if not station.claims_interact(self):
			continue
		if station.interact_priority > best:
			best = station.interact_priority
			winner = station
	if winner:
		winner.perform_interact(self)
		return
	_pick_up_or_drop()

func _pick_up_or_drop() -> void:
	if held_item:
		held_item.drop(get_parent(), global_position)
		held_item = null
		return
	var nearest := _nearest_loose_item()
	if nearest:
		nearest.pick_up(hold_point)
		held_item = nearest

func _nearest_loose_item() -> Carryable:
	var best: Carryable = null
	var best_dist := PICKUP_RANGE
	for item in get_tree().get_nodes_in_group("carryables"):
		if item.held:
			continue
		var d := global_position.distance_to(item.global_position)
		if d <= best_dist:
			best = item
			best_dist = d
	return best

BEFORE YOU SAIL

A last read, top to bottom

Each of these is a thing that has actually gone wrong in a build of this game. Walk them in order with the sandbox on.

It runs at all

  • All three autoloads are registered: GameState, PlayerRegistry, Fx.
  • pump.gd declares class_name Pump - without it leak.gd's @export var pump: Pump won't parse, and nothing else in the project will either.
  • enemy_ship.gd declares class_name EnemyShip, and its Timer child is named exactly Cadence.
  • The Output panel is clean on startup - no "node not found", no null instance.

You can see what's happening

  • Six crew are six visibly different colours, and you can find yourself without pressing a key.
  • Powder, shot, plank and bucket are four distinguishable icons - and a bucket you've just emptied on a fire looks empty.
  • Every cannon's phase light reads grey → amber → yellow → green → red, from across the deck.
  • All eight stations are visible on the deck and distinguishable from each other. An Area2D with no Sprite2D draws nothing at all - walk the corridor and confirm you can find the magazine without knowing where it is.
  • The water bar and the enemy hull bar are both on screen, and neither shakes with the camera.
  • You can tell, without reading a word, whether a gun needs powder, shot, ramming, or time.

The hazards behave

  • A fire never appears in the corridor, in a wall, or over open water, and never spreads out of the room it started in - _room_of() is the only definition of burnable anywhere in the code.
  • A leak never springs somewhere no plank can reach it.
  • Fire, Leak and Breach each join the "stations" group in their own _ready() - without it, dousing, plugging and repairing are fully written and never once called.
  • Two unplugged leaks outrun the pump; one does not.
  • The lumber crate never gets breached - breach the deck twenty times in the sandbox with B and confirm it is never the one that goes down. If it can be, the run can reach a state with no legal move.

The interactions don't fight each other

  • Two crew members can load the same cannon in relay without either dropping what they're carrying.
  • Pressing interact at a station never gets swallowed by generic pickup/drop, and vice versa - each station both claims and performs.
  • A fire burning on a station's own cell can still be doused. Light one deliberately underneath the water butt and put it out; if the station wins the press instead, interact_priority isn't being consulted.
  • Every mast's collider is exactly one tile wide - walk past all three, both directions, and through every doorway.
  • No station sits off a floor tile: flip Run Check on LayoutCheck and read the Output panel.

A battle can end, and then start again

  • Sinking the enemy shows VICTORY; flooding or a magazine fire shows DEFEAT with the right reason.
  • R restarts, and the new battle does not open already decided - GameState.reset() runs before reload_current_scene().
  • godot --headless -s addons/gut/gut_cmdln.gd -gdir=res://tests -ginclude_subdirs -gexit passes.
  • With SANDBOX = false the join screen is the main scene, and the roster it builds is the roster that boards.

You didn't build the thing you decided not to build

  • There is no helm, no heading, no closing range anywhere in the build.
  • The enemy's firing never settles into a beat you can predict.
  • No cannon has an enemy field to forget to wire.
  • Every script above is complete as printed - you never had to open a file this guide didn't show you.
